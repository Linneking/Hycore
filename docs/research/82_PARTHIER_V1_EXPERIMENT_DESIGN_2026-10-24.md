日期：2026-10-24。依据实际生产源码 `82478cd` 和已完成的启动验收整理。本文解释本次实验的研究问题、数据流、目标、训练与观察方法；执行时间线和显存排查另见[80：启动与验收记录](80_PARTHIER_V1_PLAN_AND_LAUNCH_2026-10-24.md)。本轮仅整理已有实现与记录，不新增训练或消融。

## 1. 这次实验想回答什么

本次选择从**原生 HyCoRe 出发，让真实局部特征充当跨实例关系的祖先候选**，完整训练一版 PartHier 联合方案，观察：

1. 三尺度局部、原 HyCoRe intra、跨实例 HIER、径向排序和同实例链能否共同训练。
2. 不预先指定尺度身份时，200/400/600 点的 part 分别多大比例被选为 pair 祖先 A 或 triple 祖先 B。
3. 加入历史候选后，祖先来自当前 batch 还是历史队列，其深度与年龄统计、来源比例如何变化。
4. 分类表现与上述几何指标是否同时改善，还是只出现损失下降或局部排序达标。

读者疑问:第二点，如何能得知这个代理被选为pair还是triple？他在训练过程中角色未必一直保持啊。

**答复：这里记录的是每条关系中的临时角色，不是给某个part颁发永久身份。** PartHier没有额外可训练的自由层次代理，候选是实际part的嵌入。对每条`(i,j,k)`，代码分别计算pair成本、triple成本，再分别选择候选索引`pair_idx`和`triple_idx`；落在前者就是本次A，落在后者就是本次B。

因此，同一个候选可以在关系R1中是A，在关系R2中是B，也可以在许多关系中未被选到；这些情况甚至可以发生在同一个训练步。若同一条关系中A、B选到了同一条目，则按碰撞处理，该条关系的HIER/ord为零，不进入角色诊断的有效选择计数。

第2个研究问题更精确的表述应是：**在有效A选择次数中，200/400/600各占多少；在有效B选择次数中，三个尺度各占多少。** 同一条目被多条关系重复选中会重复计数，历史队列条目也包括在内。这是“尺度在某角色选择事件中的占比”，不是“全部200点part中，有多少独立part曾担任A”。

源码的`roles.pair.scale_counts`、`roles.triple.scale_counts`可直接回答前一种问题。现有日志没有持久化全部逐关系选择，故不能据此还原每个固定part从A转为B的完整轨迹。此外，同一个对象在下一步会重新增强、重选中心，`object_id`相同不等于同一个局部。严格追踪需额外保存产生步、批次行、尺度、中心/源点索引身份及逐关系选择；本轮没有补做这类追踪，也不把总体比例解释成角色稳定性。

这是一条**单 seed 的联合方案完整实验**。它包含三尺度输入、基础 intra 合并方式及新祖先目标等多项变化，本轮没有运行匹配的无祖先目标 H0，因此结果应先解释为整体配方表现。

## 2. 固定底座，明确本次改动

| 项目 | 最终选择 |
|---|---|
| 网络 | 原 HyCoRe 的 Hype-PointMLP，共享编码器，256维嵌入 |
| 空间 | 基础与跨实例目标均用原生 c=1 |
| 输出几何 | 保留原生数值投影，**不新增 cap、tanh 软预算**、固定 whole 深度或出口 GS |
| 初始化 | seed4780，从头初始化；无 teacher，无旧模型续训 |
| 祖先表示 | 真实 part 嵌入；不增加自由层次代理参数或代理 AdamW |
| 局部尺度 | 固定 200/400/600 点，同中心嵌套 |
| 祖先角色 | 三尺度混合选 A/B，无角色尺度掩码 |
| 历史池 | 2048条 part 特征，FIFO，detach |
| 基础 intra | 每尺度的 radial、contrastive 各乘0.01，三级直接求和 |

采用这些选择，是为了落实已经确定的 v1：首先看原生 HyCoRe 上的实际训练行为。它保留了 PartHier 的真实局部祖先、混合选择、排序、链和队列结构，但没有原样照搬导师草案的全部数值映射，也没有接入 V9 的固定 whole 深度分支。

## 3. 输入和三个 part 如何组织

训练数据为 ModelNet40 官方9840个对象。每次取1024点，沿用现有缩放、平移和点序打乱增强，再按现有 whole 裁剪流程得到800–1024点的 whole。
读者疑问：为什么whole也需要被裁剪？原始数据不应该是统一的1024数据点吗?为什么有裁剪？

**答复：1024是数据加载后的基准输入长度，800–1024是训练时额外构造的whole视图长度。** 使用的HDF5版本每个对象存2048点，原版`data.py`先取前1024点，训练时再缩放、平移和打乱点序。原版`main_pointmlp_hycore.py`的实际训练代码随后连续调用两次`get_children_np`：

```python
_, whole, last_index = get_children_np(input1024, kmin=800, kmax=1024)
_, part, _ = get_children_np(whole, starting=last_index, kmin=200, kmax=600)
part_embedding, _ = net(part, emb=True)
whole_embedding, logits = net(whole)
```

这里是等价命名的摘录，实际源码位置见文末链接。第一次每步抽一个whole点数N，各对象各自抽一个中心，保留离中心最近的N个点；第二次再抽一个part点数K，各对象在各自whole内另抽中心，取K近邻。**whole的中心与part的中心不要求相同；PartHier要求相同的是三个part彼此的裁剪中心。**

因此，“whole”表示这一对训练视图中较大的父视图，不保证是最初1024点的完整集合。whole随机裁剪是原实现保留的训练操作，可以理解为视图增强；它不是点云分类的数学必需条件，其单独收益也没有在本轮隔离验证。原版标准test路径直接编码加载后的1024点，不执行这两次训练裁剪。

还要看清`get_children_np`的内存行为：它先取`part = whole[:, :, :K]`这个**共享存储的视图**，再将所选K近邻写进part。所以写part也会改变whole的前K个位置。它不是对嵌入向量某些维度覆写，而是对编码器之前的原始点坐标覆写。完成后先编码part，再编码已被修改的whole。

**原版点数的补充审查：** 训练入口明确传入`kmin=200, kmax=600`，函数内部执行`K=random.randint(200,600)`，含两端，共401种整数点数，均匀分布的期望是400。每次训练迭代重新抽一次K，同一batch各对象共用这个K，但各自抽取中心；不是每个对象分别抽一个点数，也不是按epoch固定K。whole的N同样每步从800–1024抽取一次。函数定义的默认范围100–500以及旁边遗留的“50–600”注释都不应覆盖实际调用参数。

覆写确实写入前K个位置，即一次索引赋值`pos_child[id,:,:] = data[id,:,idknn[id,center,:]]`；不是训练token、不是编码后的256维特征，也不是每写一个位置就重新选一次近邻。以N、K独立均匀抽样的口径，期望前缀写入位置占比为`E[K/N]≈44.08%`，单步范围约19.53%–75%。这不等于有44.08%的不同源点消失：可能有位置写回原值，也可能是所选点重新排列。

更准确地，若W0有N个互异源点、I为所选K个索引，覆写后丢掉的不同源点数等于新增重复次数`D=|I ∩ {K,...,N-1}|`，不同源点数为`N-D`，且`D≤min(K,N-K)`。这一行为会改变密度、覆盖和FPS输入布局，值得单独审查；仅凭“原版也这样”不能证明它有益。源码能确认这是共享存储导致的实际操作，不能据此断言它一定是作者有意设计的密度增强。其分类影响需对照保留覆写与独立clone两个路径判断，本次没有开展训练消融。

对每个对象执行一次如下流程：

1. 保存 part 覆写前的 whole 独立副本，作为此次三个尺度的共同裁剪源。
2. 在这个副本中随机选择一个中心，只计算一次有序的600近邻。
3. 取这份有序索引的前200、前400、前600，得到三个 part。
4. 将有序600点覆写到实际 whole 的前600个位置一次，whole 后缀保持不变。
5. 为三个 part 分别建立独立输入副本，再按200→400→600→whole顺序编码。

读者疑问：第二点：随机中心为什么能保证取到前六百近邻？第三点：索引顺序能保证不同大小part是同一个中心的吗？第四点：为什么这种构建的part，只需要用600覆盖一次whole就可以了，是因为200 400都和600部分重复吗？第四点：这个编码顺序有什么意义和影响？
读者建议：为我理清原始hycore选择part与覆盖whole的逻辑。对比检查我们parthier有没有太武断之处。

**答复一：这里是固定数量的KNN，不是固定半径内找点。** 冻结的whole有N≥800个点；无论随机选中哪一个查询中心，都能对这N个位置计算到中心的距离并选出最近600个索引。最远的入选点可以很远，算法不保证600点落在某个预设半径内，也不保证它们构成某个语义部件。当前实现沿用原版负平方距离/topk，先计算whole两两距离再取中心对应的邻居行；“一次”指三个part共用这一次600近邻选择，不表示完全省掉了两两距离计算。

**答复二：同中心来自同一次查询，嵌套来自共用同一份有序列表。** 对某个对象只抽一个part中心c，得到按到c的距离由近到远排列的索引`I=[i1,...,i600]`，再取`I[:200]`、`I[:400]`、`I[:600]`。三个尺度的KNN查询中心都是c；这不要求三个点集的坐标均值/几何重心也相同。距离相等时的排列可由topk决定，但三个尺度使用同一列表的前缀，嵌套仍成立。只说“索引有序”还不够，关键是不能三次各换一个中心或各用变化后的父输入。

**答复三：一次600覆写足够，是因为200/400完全是600的对应前缀，而不只是部分重叠。** 设冻结whole为W0，先构造`S=W0[:, :, I]`，再执行：

```text
W[:600] = S
P200 = clone(W[:200])
P400 = clone(W[:400])
P600 = clone(W[:600])
```

这时600的位置布局已经包含了200、400所要求的全部布局。若用同一份冻结源和同一列表，再将200、400写回对应前缀，写入的值与已有值相同，没有额外作用；若重新抽中心或在已修改的whole上重做KNN，就不再保证相同。因此不是把三个part拼接成1200点，也不需要把三个副本依次再次覆写父输入。

**但“保留后缀”不等于保留whole原有的全部不同点。** S中的一些源点可能原本也在后缀里，覆写后会重复出现；原前缀中未被S选择的点则可能消失。用8个源点编号作示意：

```text
W0          = [0, 1, 2, 3, 4, 5, 6, 7]
选出的6近邻 = [4, 3, 5, 2, 6, 1]
覆写后的W  = [4, 3, 5, 2, 6, 1, 6, 7]
```

W仍有8个位置，但只有7个不同源点，6重复而0消失。原版单part覆写也有这种行为；PartHier固定用600点覆写，属于沿用原机制并固定了该机制的尺度，不是证明这种点密度处理最优。在原始源点互异时，覆写后的不同源点数为`N - |I ∩ {600,...,N-1}|`，至少600；实际应区分位置数、不同源点数和不同坐标数。

**答复四：200→400→600→whole是四次独立编码的调用次序，不是递归特征传递。** 编码器参数共享，但600分支不会读取400分支的特征，whole也不会读取600分支的特征；四次前向后统一计算损失、反传和更新。嵌套在前向之前已经完成，输入各自clone，次序不负责制造包含关系。

原版是`part→whole`，本版将它扩展为小到大三个part后再whole。主要可确认的次序影响是共享BN的运行统计：训练态普通BN用本次输入的batch统计归一化，同时按`running_new=(1-m)*running_old+m*batch_stat`更新评估用统计。因此换序会改变最终running buffer，且后出现的whole在这串EMA更新中权重更近；不能说whole使用了前面part的running均值来完成普通训练态归一化。如果网络含随机层，调用顺序还可能改变随机数的分配。现有设置每步四次有效BN更新，原版只有两次；本轮没有单独证明此顺序优于其他顺序。

因此，按源点索引有：

\[
P_i^{200}\subset P_i^{400}\subset P_i^{600}.
\]

这个设计满足三个part同查询中心、源点索引嵌套和part位于whole前缀的构造约束，避免连续调用三次会覆写父输入的裁剪函数，令后一次裁剪源发生变化。它不保证语义嵌套、whole不同点集合不变或编码后自动形成特征树。

PointMLP内部保留原有分组数，首层仍请求512个采样中心；200/400点输入可能重复采样中心。本轮没有随输入尺度修改网络内部采样结构。

读者疑问：pointmlp的512采样中心是什么意思？我们parthier的设置相较于hycore，在这上面有多大影响？

**答复：512是PointMLP第一阶段要建立的局部特征组数，与上面的一个裁剪中心不同。** 本地`Hype_pointMLP`从名义输入1024设置四个阶段，FPS中心数固定为512→256→128→64。第一阶段先用最远点采样FPS从当前输入选出512个中心索引，再为每个中心找24个近邻，分别编码和聚合局部特征。[PointMLP论文](https://arxiv.org/abs/2202.07123)可作网络背景，实际数值以本地`Hype_pointMLP`构造和`LocalGrouper.forward`为准。

随机KNN裁剪解决“送给编码器哪一片点”；FPS解决“在这片输入里，用哪些位置建立局部特征组”。FPS不会把200点创造为512个不同的新点。当前CUDA算子会返回512个输入索引，输入索引不足512时只能重复；至少重复的索引位置数如下，实际可因输入重复/退化更多：

| 输入分支 | 输入位置数 | 第一阶段请求数 | 最少重复索引位置数 |
|---|---:|---:|---:|
| part200 | 200 | 512 | 312（占512的60.94%） |
| part400 | 400 | 512 | 112（21.88%） |
| part600 | 600 | 512 | 0下界，不保证实际为0 |
| whole | 800–1024 | 512 | 0下界，不保证实际为0 |

本地CUDA FPS从输入索引0开始，所以前缀布局也可能影响FPS起始位置；不能把坐标覆写理解为任意打乱后绝对等价的集合操作。本文不假设所有源坐标互异或FPS一定覆盖全部不同位置。

**原版HyCoRe已经存在“小part不足512”的情况**：它随机取200–600点的part，内部仍请求512中心。PartHier没有新引入这个算子行为，但让200、400两条低点数分支每一步都参与，而且从一个part分支变成三个；重复中心/邻域可能影响局部统计、梯度累加和计算开销。三级part都使用相同的512→256→128→64组数，并不意味着它们具有相同的信息量。不能直接认定它导致精度下降，也不能把“网络配置未改”写成“对训练没有影响”。

### 3.1 与原版的边界及本次核对

| 项目 | 原版HyCoRe | PartHier v1 | 判断 |
|---|---|---|---|
| whole训练裁剪 | 1024中取800–1024近邻 | 保留 | 沿用，不是本版新加 |
| part个数/尺度 | 每步1个，点数随机200–600 | 每步固定200/400/600，同中心嵌套 | 新的输入与监督分布 |
| 坐标覆写 | 所选K点写入whole前K位置 | 所选600点写入whole前600位置一次 | 原机制的固定大尺度扩展 |
| 小part的FPS | 仍请求512，可能重复 | 相同算子，200/400每步出现 | 旧边界条件被固定分支反复使用 |
| 前向/有效BN | part→whole，2次 | 200→400→600→whole，4次 | 新的统计与计算负担 |
| intra | 一个尺度，各项0.01 | 三个尺度逐级各项0.01求和 | 相对单尺度加大了基础intra总量 |

这些选择有明确实现和可核对的构造约束，但**“实现不含矛盾”不等于“实验选择已经最优”**。同中心的几何嵌套不保证语义部件嵌套，600覆写/四次BN/固定512中心的组合效果也没有被H0和单因素实验隔离。不能只把整套方案的结果归因真实part充当祖先。

2026-10-26本机只用CPU复核：已有3项裁剪/副本/四次BN合同全部通过；另外直接从原版`hutil.py`提取实际`knn`和`get_children_np`函数，固定相同whole与part中心，并将原版单part数设为600，得到的whole、600点part与PartHier逐元素相同，200/400也与该part对应前缀相同。两条合成输入的whole均为900个位置，但覆写后只有711/696个不同源点，印证重复/丢点机制；这些是合成CPU实现核对，不是训练数据分布统计或分类消融，也没有GPU前向/训练更新。

### 3.2 为什么不同大小的part可以共用BN

**BN不只在test时使用。** 训练态BN会用当前输入的均值/方差进行归一化，并通过该计算参与反向传播；可训练的逐通道缩放γ、平移β由优化器更新。同时，运行均值/方差是buffer，在前向时按EMA更新、供默认eval路径使用，不由优化器通过梯度学习。[BN原论文](https://arxiv.org/abs/1502.03167)与[PyTorch 2.8说明](https://docs.pytorch.org/docs/2.8/generated/torch.nn.BatchNorm1d.html)分别说明其训练作用及具体接口。

对输入特征`X[B,C,N]`，BatchNorm1d按通道c统计B和N两个维度上的数值，`μc=mean_{b,n} X[b,c,n]`，再用对应方差归一化。需要保存的γ、β、running_mean、running_var都只有C个数，不是N个数。因此`[32,64,200]`和`[32,64,900]`都能送进同一个64通道BN；点数不同改变参与统计的观察值数量，不改变参数形状。池化后投影处的`[B,512]` BN则只在batch维度统计，每个通道同样保存一个均值/方差。

原版`net.train()`后调用同一个网络两次，没有对part分支单独关闭BN更新，所以part和whole都会归一化、更新同一组buffer。这是共享训练态模块的直接行为，不必先假定作者做过“让part参与test统计更好”的专门验证。每次调用是一次EMA更新，不会自动按原始输入点数把900点分支加权成200点分支的4.5倍；轮流更新的方差也不是所有视图合并后重新精确计算的总体混合方差。

因此应分开两个问题：两个分支训练时如何被归一化，以及评估whole时使用哪种运行统计。共享BN允许不同N，但不保证不同尺度的特征分布一致；分布错配是待验证的可能影响，不是本轮精度退化的既定原因。CPU独立演示中，同一3通道BN连续接收`[4,3,200]`、`[4,3,400]`、`[4,3,1024]`，buffer和γ始终为长度3，计数依次1、2、3。

**三个 part 是同一个对象的三个输入视图，不是预先给 whole 安排三个树父节点。**它们先进入候选池，之后由每条跨实例关系重新选择祖先。

## 4. 谁选择谁：关系和候选池分开建立

### 4.1 whole 三元组来自当前 global64

每步从40类中均匀抽取32个不同类别，每类有放回抽2个对象，共64个；两卡各分到16类×2个，类别在两卡间不重叠。它是非循环类别均衡抽样，一轮200次更新不等于把9840个对象无放回遍历一次。

用当前64个 whole 嵌入建立相似度：

\[
s_{ij}=\exp[-d_1(u_i,u_j)]+\mathbf 1[y_i=y_j].
\]

随后沿用现有 HIER 关系挖掘：

- 每个 whole 取 top-K=20，K的口径包含自身，再去掉互近邻矩阵的对角线。
- 互为近邻的 whole 构成正关系候选；至少有两个非自身互近邻的 anchor 才参与抽样。
- 对每个有效 anchor，分别有放回抽50个 j、50个 k，配成 `(i,j,k)`；j来自互近邻，k来自非互近邻且排除批次位置上的 k=i。
- 标签在相似度中提供偏置，j并不被硬性限定为同类，k也不被硬性限定为异类。

因此，关系查询的范围是**当前 batch 的64个 whole**，历史 whole 不参与这一步。最多产生64×50条关系，实际条数由有效 anchor 数决定。关系索引挖掘本身不反传。

### 4.2 祖先来自当前 part 与历史 part

当前 batch 提供：

\[
\mathcal C_t^{\rm live}=\{v_i^{200},v_i^{400},v_i^{600}\}_{i=1}^{64},
\qquad |\mathcal C_t^{\rm live}|=192.
\]

再拼上最多2048条历史 part，形成：

\[
\mathcal C_t=\mathcal C_t^{\rm live}\cup Q_t,
\qquad |\mathcal C_t|\le2240.
\]

这里的容量单位是**part条目**，不是独立对象数；没有按对象去重，也没有排除当前查询对象自身的 part 或其历史条目。三个尺度都可以竞争 A，也都可以竞争 B。

对每条关系，定义候选 p 的两种成本：

\[
c_A(p)=\max\{d(u_i,p),d(u_j,p)\},
\]
\[
c_B(p)=\max\{d(u_i,p),d(u_j,p),d(u_k,p)\}.
\]

分别独立做一次 hard Gumbel/ST 选择得到 A、B。实际代码的软概率为：

\[
s_A=\operatorname{softmax}(-c_A/\tau+G_A),\qquad
s_B=\operatorname{softmax}(-c_B/\tau+G_B),\quad \tau=0.1.
\]

G为单位Gumbel噪声；这里沿用现有实现，成本先除以0.1，噪声没有同时除以0.1。前向使用真实候选条目，反向使用soft概率的ST梯度。距离和深度的选择保持同一份hard/ST选择，不对候选点坐标求软平均来构造新祖先。

若A、B选到同一个候选索引，该关系的 HIER 和 ord 都置零，但均值分母仍保留所有抽样关系。不同索引即使来自同一对象，也不按这种碰撞处理。

### 4.3 队列如何更新

先用本步前向特征计算目标、反传并更新编码器，再把**刚才前向得到的192条 part 特征**detach入队；没有在更新后重新编码，也没有EMA编码器。FIFO超过2048条时丢弃最旧条目，稳定后历史条目一般来自约1–11个更新步以前。

队列保存嵌入、object_id、尺度和产生step。当前192条候选保留编码器梯度；历史条目不向旧计算图反传，whole查询和可微选择路径仍可影响当前网络。两rank按同一全局顺序各维护相同队列，按轮检查其哈希一致性。

从空队列开始，第11次更新后填满；**第12步才首次在前向中使用完整2048条历史候选**。

## 5. 损失如何组合

记 whole 嵌入为u，局部嵌入为v，径向深度为：

\[
r(x)=d_{\mathbb H}(0,x),\qquad r(x)=2\operatorname{atanh}\|x\|\quad(c=1).
\]

最终总目标固定为：

\[
\boxed{
L=L_{\rm CE}
+0.01\sum_{g\in\{200,400,600\}}(L_{\rm rad}^{g}+L_{\rm con}^{g})
+0.5L_{\rm HIER}
+0.1(L_{\rm ord}+L_{\rm chain})
}.
\]

CE只作用于whole分类，标签平滑沿用现有实现ε=0.2。损失系数和间隔没有根据短测分类成绩搜索。

### 5.1 三级原 HyCoRe intra

\[
L_{\rm rad}^{g}=\frac1{64}\sum_i
\left[r(v_i^g)-r(u_i)+\frac{1000}{N_g}\right]_+.
\]

N为该尺度点数，故200/400/600对应的径向间隔为5、2.5、5/3。

\[
L_{\rm con}^{g}=\frac1{64}\sum_i
\left[d(u_i,v_i^g)-d(u_i,v_{\pi(i)}^g)+4\right]_+,
\qquad\pi(i)=63-i.
\]

这里的anchor是whole，负例是**同一尺度的另一对象part**；不是以part为anchor，也不是跨尺度混合负例。批次的类别分块顺序保证global flip负例异类。三级分别算全局64均值后相加，不平均成单尺度权重。

### 5.2 跨实例 HIER

对关系 `(i,j,k)`，在A≠B时使用：

\[
H_{ijk}=[d(u_i,A)-d(u_i,B)+0.1]_+
+[d(u_j,A)-d(u_j,B)+0.1]_+
+[d(u_k,B)-d(u_k,A)+0.1]_+.
\]

它要求i、j更接近pair祖先A，而k相对更接近triple祖先B。按前述碰撞掩码后，对全部抽样关系取均值，得到L_HIER。

### 5.3 祖先径向排序 ord

\[
O_{ijk}=[r(A)-\min(r(u_i),r(u_j))+0.2]_+
+[r(B)-r(A)+0.2]_+.
\]

仍以相同碰撞掩码、全部关系分母得到L_ord。当前目标只包含A浅于i/j较浅者、B浅于A两项；**B是否也浅于k只做诊断，没有加第三个hinge**。

### 5.4 同对象多尺度 chain

\[
L_{\rm chain}=\frac1{64}\sum_i\big(
[r(v_i^{200})-r(v_i^{400})+0.2]_+
+[r(v_i^{400})-r(v_i^{600})+0.2]_+
+[r(v_i^{600})-r(u_i)+0.2]_+\big).
\]

三个相邻hinge先求和，再对对象取均值。chain约束同一个对象的局部链；ord约束每条跨实例关系中选出的A/B。两者都没有给尺度分配固定角色，也都是可被违反的软目标，因此训练后需要检查满足率，不能把加了损失写成已经构建出全局离散树。

实现中，关系挖掘、基础intra和HIER正式距离沿用各自既有的c1数值实现，稳定项并非逐算子完全相同。基础intra保留原hinge在精确零点的梯度处理；这些细节没有作为本轮调参变量。

### 6.1 为什么本版没有代理AdamW，以及它意味着什么

**先区分“损失”与“被优化的参数”。** 原版官方HIER常用AdamW统一管理视觉编码器、监督损失参数和独立层次代理的参数组；官方实现也提供SGD、Adam等分支，并不要求HIER数学目标必须绑定AdamW。我们之前移植到HyCoRe的方案则拆成：共享网络θ用RiemannianSGD，独立切空间代理φ用AdamW。

PartHier用`v=fθ(part)`这样的实际编码结果替代自由代理φ，HIER/ord/chain模块自身没有可训练参数，所以不是保留了φ却不更新它，而是φ这组参数及其AdamW一起取消了。当前所有目标的梯度汇总到共享θ，再由RiemannianSGD统一更新；历史队列只是detach特征缓存，没有为每条历史part维护AdamW状态。

| 比较项 | 本版RiemannianSGD | 原移植HIER的代理AdamW |
|---|---|---|
| 参数对象 | 共享编码器/投影/双曲嵌入/分类层θ | 独立代理切空间参数φ |
| 梯度历史 | momentum=0.9 | 一阶矩与二阶矩，betas=(0.9,0.999) |
| 坐标自适应 | 无Adam式逐坐标二阶矩分母 | 按`sqrt(v_hat)+eps`逐坐标缩放 |
| 权重衰减 | 当前实现将L2项加入梯度，再参与更新 | W表示独立weight decay，不累计进m/v |
| 几何处理 | 对ManifoldParameter按其流形更新；普通参数走欧氏分支 | 普通AdamW，φ在欧氏切空间中存储，几何映射/GS由前向反向模块另做 |
| 历史配方数值 | lr0.1、WD2e-4、余弦至0.005 | A0：lr0.01/eps1e-8；A1：lr0.005/eps1e-4；WD0.01，余弦至0.0005 |

不能直接按lr0.1与0.005推断谁的实际位移大，因为二者把梯度变成位移的规则不同。AdamW的适应项为`-lr*m_hat/(sqrt(v_hat)+eps)`，另有`-lr*weight_decay*parameter`；它的解耦衰减是通用优化设计，不是HIER专用稳定器。[AdamW论文](https://arxiv.org/abs/1711.05101)、[PyTorch 2.8算法说明](https://docs.pytorch.org/docs/2.8/generated/torch.optim.AdamW.html)。

**当前RiemannianSGD的名字也不能等同于“全部参数都住在双曲球上”。** 冻结的实际生产网络在CPU构造审查中有126个可训练参数张量，全部是普通Parameter，无可训练ManifoldParameter/ManifoldTensor；38层BN，PartHierarchyLoss可训练参数数为0。默认Mobius层`over_param=False`，曲率冻结。因此本配置优化器对这些参数走欧氏分支；输出中的双曲几何仍通过模型运算和反传体现，不会凭优化器名称自动新增出口GS或Adam式自适应。

**取消独立代理优化，实质上也取消了独立移动祖先的自由度。** 旧φ可以在不直接改变编码器的情况下被AdamW移动，并单独设置学习率；本版祖先来自共享编码器，当前part、whole和各项监督共同决定θ的更新。新目标的梯度是否竞争、这种耦合是否更难优化，要实际测量，不能由“没有AdamW”直接判断。把同一个θ分别交给RSGD和AdamW、按不同损失各走一步，也不是原联合更新的等价替代。

AdamW可能通过动量、自适应缩放和独立衰减改善某些参数的优化，但不保证更稳定；RSGD也已有动量。特别是eps很小时，小梯度可被二阶矩归一化为相对较大的更新，历史m也可能在当前径向梯度很小时继续推动代理。cap、GS、梯度裁剪和学习率调度是独立组件，不属于AdamW自带的层次或双曲保护。

我们的[88号eps单变量十轮审查](88_B05_EPS_ONLY_10E_2026-10-25/report.md)提供了直接证据：固定代理LR0.005，仅eps1e-8→1e-4，第10轮raw模长越cap代理从500/512变为0/512，首步相同梯度下参数更新L2从1.79944降到0.446155。它支持eps影响代理更新与越cap行为，不证明AdamW一定优于RSGD、没有完整分类结论，也不能直接外推PartHier没有自由代理时的结果。官方HIER代码在启用fp16时用eps1e-4、否则1e-8，这也说明具体数值配方必须单列；不能只比较优化器名称。

若以后要比较共享网络改用AdamW，应该保持同一PartHier结构和输入预算，从头做优化器控制，并重新匹配学习率、衰减和调度；那检验的是整个共享网络的优化方案。若增加独立part投影头或重新引入自由代理再交给AdamW，则还改变了模型参数化，不能称“仅恢复HIER优化器”。本次没有修改优化器或启动该实验。

| 四路主干均重算 | 18.07GiB | 26.46GiB | 1.527s |
| 仅200/400主干重算，600/whole保留（采用） | 27.79GiB | 28.21GiB | 1.343s |

采用第二种，有界短测少耗时约12%，设备空闲至少约2.27GiB。重算时使用临时BN buffer并恢复RNG，使反向额外计算不增加有效BN统计更新。它只决定中间激活如何保存，不作为层次方法的科研消融；短测步时也不等于完整300轮稳定吞吐结论。

正式首轮已通过全部保存状态验收。最新实证是启动和首轮可运行性，不是完整300轮效果；本说明未重新采集当前训练进度。

## 9. 结果怎么读，以及还不能归因什么

分析时分开三类变化：

| 类别 | 本次内容 | 如何解释 |
|---|---|---|
| 实现正确性与工程保持 | 冻结裁剪源、独立副本、全局梯度归一化、ST/碰撞分母、BN中性重算 | 证明代码实现了既定目标，不能直接计作科研收益 |
| 基础训练协议变化 | 固定三级part、600覆写一次、四次BN、三级intra求和；相对旧V9还改为原生c1直接参与inter | 会改变基础训练，不能都算成换祖先的贡献 |
| 祖先目标与候选机制 | 真实part的HIER、ord、chain、历史队列 | 本轮只观察联合效果，尚无组件因果拆分 |

现有记录支持以下观察：

- **分类**：best轮OA及同轮AA、终点、逐轮趋势；明确标记TS，不能写成validation选模。单seed不提供跨seed方差。
- **优化**：CE、逐尺度radial/contrastive、HIER/ord/chain、加权总量、裁剪前后范数、有效关系和A=B碰撞率。
- **几何**：whole、各尺度part、A/B的深度统计，ord两项和chain三项达标率；B<k另列诊断。
- **角色与队列**：A/B的三尺度选择计数、当前/历史来源比例、年龄、条目覆盖，以及祖先来自查询后代对象的比例。按候选池本身的尺度构成一起解释。

当前没有为每个历史part保存完整裁剪中心/点索引，也没有持久化所有逐关系祖先选择；这些总体统计不足以直接还原每个历史局部或确认某个固定part的完整身份转换轨迹。独立局部对应、形态语义共享验证也尚未进行。分类提升、损失下降和径向达标分别回答不同问题，不能相互替代。

若后续要判断新祖先目标的净贡献，首先需要一条**匹配H0**：同样三尺度、裁剪、三级intra、四次BN、采样、seed、优化器、预算和选模，只去掉HIER/ord/chain。该对照目前只是建议，没有启动。历史单part或其他seed/batch的实验可作参照，不能替代这个控制。
