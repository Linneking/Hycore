# V5/V6 H20：whole 嵌入与代理近邻集中诊断

2026-10-06，现有缓存的 CPU 只读分析。没有模型 forward、反向传播、优化器更新或新主训练；原权重和全部输入缓存的 SHA256 在分析前后保持一致。诊断代码提交 `6e77c59`，分支 `codex/hier-whole-cache-diagnostic`。

**主要发现：近四检索集中首先是一种强烈的径向检索偏置；不能仅据此判定所有代理坐标重合，也不能把它直接等同于实际祖先使用退化。** V6 最终 dresser 的 whole 比 B32/B64 的相同实例更靠中心，同时类内方向更分散。这个差异是类别相关的，而不是全体 whole 统一向外或向内移动。现有基线仍不能隔离 HIER 的训练因果效应。

## 1. 数据身份和比较范围

使用四份 H20 clean eval 缓存：V5 e200、V6 best99/e200/e300；另用历史 HyCoRe B32 best229/last300、源码 B32 best216/last300、B64 best267/last300，共十份缓存。每份都取 **相同 8856 个 H20 训练实例**，不包含验证或 test 的结构选模。

发现并处理了跨分析的 ID 编号差异：H20 以排序后的训练 HDF5 文件拼接编号，原/B64 分析保留 glob 文件读取顺序。直接用数值 ID 对齐，只有 332/8856 个标签相同。此次以 **文件名＋文件内行号** 重建统一身份，核对文件列表、唯一性和全部标签；十份缓存均通过 8856/8856 标签一致性检查。旧 26 中各模型间采用相同 glob 顺序的比较不受这个跨分析问题影响。

所有距离、角度及半径均在原 256 维空间计算，将缓存 FP32 向量转成 NumPy FP64。模型输入均为原始前 1024 点、无增强、eval 模式；本次不重跑模型。源码实际使用原生 CUDA FPS，未启用源码中注释掉的随机起点 Python FPS。whole 在 eval 下不受 BN 批成员统计更新影响；既有 train/eval BN 差异仍不能由本次缓存分析排除。

B32/B64 和 H20 的数据量、抽样、更新预算和选模口径不同。固定相同评估实例使几何差异可比较，**没有把不同训练协议变成仅改变 HIER 的消融实验**。best 权重轮次也不同，报告中保留 best/last 身份。

## 2. 冻结检索控制定位了主要影响因素

每份 H20 都固定其原有合格代理集合和全部 8856 个 whole，展示数固定为四个不同 ID。只改变诊断副本的半径或候选池，不重新判断代理资格，不更新模型。检索不加类别标签分数。

| H20 权重 | 合格代理 | 原距离覆盖 ID | whole 等半径覆盖 ID | proxy 等半径覆盖 ID | 借用 B32 半径覆盖 ID | 移除最低半径 1% 后覆盖 ID |
|---|---:|---:|---:|---:|---:|---:|
| V5 e200 | 165 | 20 | 91 | 22 | 21 | 38 |
| V6 best99 | 188 | 30 | 328 | 37 | 38 | 76 |
| V6 e200 | 188 | 39 | 173 | 41 | 31 | 65 |
| V6 e300 | 485 | 28 | 190 | 30 | 28 | 51 |

等半径为欧氏半径 .98，方向不变。对于固定非零代理，所有 whole 半径相同之后，双曲近邻排序与余弦方向排序严格同序；此次两种计算的 top4 ID 完全一致。两者是同一个控制的数学复核，不是两份独立证据。

V6 e300 的同一最大近四集合在原距离下被 **373/485** 个合格代理重复检索；统一 whole 半径后降为 **53/485**，统一 proxy 半径后仍为 **367/485**。原检索的有效实例数量为 7.13，whole 等半径后为 53.04。方向控制仍有集中，不能说径向因素解释了所有集中现象。

两个额外控制说明这不只是几个坏样本的问题：

- **删除最低半径 1%。** e300 删除 89 个实例后，出现新的四个 dresser 热点；仍有 281/485 个代理共享一个近四集合，87.68% 的槽位来自剩余候选中最低半径约 1%。其他三个 H20 也有同样的“下一个低半径集合接替”现象。
- **借用正常 B32 的半径。** 保留 H20 的方向和代理，仅将每个 whole 的半径替换为相同 ID 在源码 B32 best216 中的值。e300 的热点转为 flower_pot、door、bookshelf、bench 等实例，集中没有消失；99.95% 的槽位来自借用半径最低约 1% 的候选。这里没有借用 B32 的方向，不能描述成“原 B32 完整嵌入也发生同一代理退化”。

因此，径向异质性与当前代理位置相互作用形成近邻热点；这种检索机制并非只有 HIER 产生的特殊半径分布才能触发。仅改变 proxy 半径、删除几个极端样本，都没有充分解决当前检索集中。

## 3. whole 发生的变化是类别和阶段相关的

| 权重 | 全部 whole 深度中位数 | dresser 深度中位数 | dresser 类内夹角中位数 |
|---|---:|---:|---:|
| V5 e200 | 4.898 | 4.992 | 7.69° |
| V6 best99 | 6.213 | 6.213 | 23.41° |
| V6 e200 | 5.352 | 5.629 | 13.13° |
| V6 e300 | 4.617 | 3.558 | 18.76° |
| 源码 B32 best216 | 4.645 | 4.702 | 6.69° |
| 源码 B32 last300 | 4.360 | 4.399 | 3.21° |
| B64 best267 | 4.478 | 4.394 | 3.57° |
| B64 last300 | 4.684 | 4.568 | 2.97° |

深度是 `d₀(x)=2atanh(||x||)`，不是欧氏半径；夹角是在原点比较单位方向。同类角度使用全部不同实例的无序 pair；全类汇总按 pair 池化，dresser 表仅使用 180 个共有训练实例。

e300 全部 whole 深度中位数与 B64 last 接近，但 dresser 明显更浅，方向却更宽。故本次证据不支持“全体 whole 更向外且类内统一挤成一点”的单一解释。

被反复检索的四个 dresser，其深度变化如下：

| 统一 ID | V6 best99 | V6 e200 | V6 e300 | B32 last300 | B64 last300 |
|---|---:|---:|---:|---:|---:|
| 2883 | 6.213 | 5.601 | 2.482 | 3.931 | 4.569 |
| 6009 | 5.243 | 6.213 | 2.407 | 4.434 | 4.364 |
| 7985 | 5.933 | 5.462 | 2.566 | 3.421 | 4.447 |
| 9123 | 6.147 | 3.474 | 2.201 | 4.077 | 4.729 |

这些样本在 V6 e300 的欧氏半径约 .801–.857，远小于全体中位数约 .980。它们相对本类平均方向的夹角约 15.0°、27.0°、22.7°、19.4°；不能把“被很多代理检索”解释成“最接近类方向原型”。单个样本的选择次数分别为 414、417、398、456/485 个代理。

跨权重的类内 kNN5 也发生较大重排。例如 V6 e300 相对 B64 last，方向邻居平均 Jaccard 为 .0421，双曲邻居为 .0414；相对 V6 best99 分别为 .0519/.0495。不同训练权重和近邻并列/微小差别可能影响这些值；本次没有独立形态真值，不能判定重排是改善还是破坏。

## 4. 为什么不把独立 UMAP 图当主要诊断

不同模型的嵌入可整体旋转，独立降维又可任意改变轴、比例和布局。直接把跨模型 2D 坐标画成位移箭头，可能把坐标选择误当成训练效果。

本次交互图同时提供：同 ID 的深度散点、十份权重的全量类内深度分位数、全量类内夹角分位数、固定代理的检索控制。改变 H20 权重、参照权重和类别可查看同一对象或类别在不同状态下的几何量。散点为固定每类 24 个实例加主要检索热点；分位数与检索覆盖均为全量计算。大点表示该实例进入合格代理近四检索的次数，不是实际祖先选择次数。

交互图初始显示 dresser 与 V6 e300/B32 last300；其他类别不会因展示选择而被排除。浏览器验证了选择交互、数据更新、JavaScript 无运行错误，以及 320px/桌面宽度无横向裁切；图中度量不由 2D 散点位置反推。

## 5. 诊断范围与下一步实验问题

必须区分：**proxy→whole 近四检索、whole→最近 proxy 分配、训练 pair/triple 的 hard-Gumbel 祖先选择**。本次新增控制针对第一种；历史 V6 已记录后二者的统计，见 22。许多代理检索同一组 whole 不等于坐标重合；此前同集合代理的双曲距离仍很大，本次复核合格代理也没有距离 ≤1e−6 的重合 pair。

已有证据定位了检索的径向因素，但还不能回答“哪个目标使这些 dresser 的 whole 变浅”。后续优先：

1. 在固定数据、训练/eval BN 模式和相同 whole/part 配对下，分解 CE、intra、HIER sample 对 whole 的实际径向/角向梯度；分别检查特定 dresser 热点与普通实例。仅 whole 的偏导不能替代共享 backbone 参数的实际梯度。
2. 冻结 whole 与同一 proxy 起点，分解 sample/proxy 目标如何移动代理，再判断角向分工、边界投影和祖先端点重合是否为剩余集中来源。
3. 若补主训练，仍需同 V6 balanced64 协议的零 HIER 对照，或者审阅后从相同前 20 轮状态分叉，固定优化器、数据/增强和 RNG 流。现有 shuffle B64 不替代它。
4. 形态解释应增加独立几何/语义验证，并展示实际 pair/triple 选中代理的端点集合；代理全局最近四个 whole 只能作检索审查。

等半径、半径替换和删除样本均是本次冻结控制，**未成为新的训练规则**。没有自动排队上述梯度检查、代理优化或主实验矩阵。
